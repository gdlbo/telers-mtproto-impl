# tellers-mtproto-impl

Runtime-neutral, low-level MTProto building blocks for the Tellers ecosystem.
The workspace consumes the published `tellers-mtproto` declarations generated by
[`tellers-tl`](https://github.com/tellers-project/tellers-tl); it does not copy TL
schemas or keep a global API constructor table.

## Crates and dependency graph

```text
tellers-mtproto (generated declarations)
└── tellers-mtproto-codec

tellers-mtproto-crypto ───────────┐
                                  ├── tellers-mtproto-transport ──┐
tellers-mtproto-session ──────────┼───────────────────────────────┼── tellers-mtproto-engine
tellers-mtproto-codec ────────────┘                               │
                                                                  │
codec + crypto + session + transport + engine ── tellers-mtproto-testkit
```

- `tellers-mtproto-codec`: bounded TL primitives, bare/boxed extension traits,
  flags, dependent lengths, generic vectors, recursion, and constructor errors.
- `tellers-mtproto-crypto`: SHA-1/SHA-256, AES-256-IGE/CTR, MTProto 2.0 message
  envelopes and KDFs, quick-ack tokens, RSA fingerprints/RSA_PAD, bounded `pq`
  factorization, DH validation/derivation, salts, and OS randomness.
- `tellers-mtproto-transport`: abridged, intermediate, padded-intermediate, full,
  and HTTP framing; quick acknowledgements; direct/MTProxy client obfuscation;
  and a synchronous runtime-adapter boundary.
- `tellers-mtproto-session`: auth key, salt, IDs, sequences, bounded replay
  history, acknowledgements, clock repair, migration, reconnect state, and
  persistence traits.
- `tellers-mtproto-engine`: typed method adapters, encrypted/plain envelopes,
  raw containers, bounded `gzip_packed`, acknowledgements, correlation, retries,
  RPC error advice, and authorization transition orchestration.
- `tellers-mtproto-testkit`: fake connections, deterministic time/randomness,
  malformed fixtures, Telegram's official authorization vectors, and Telegram
  Desktop behavioral parity regressions.

Every crate is MPL-2.0 and forbids unsafe Rust. Public failures use typed errors;
no core crate depends on Tokio, async-std, `anyhow`, or `eyre`.

Each crate root is a small documented façade. Implementation is organized by
responsibility rather than accumulated in `lib.rs`:

```text
codec/      decoder · encoder · error · traits · value
crypto/     symmetric · message · rsa · dh · error
transport/  common · framing · obfuscated · http · connection
session/    state · receive · ports · error
engine/     wire · rpc · rpc_error · authorization · error
testkit/    time · connection · fixtures
```

Unit/property tests live in per-crate `tests.rs` modules, while source-derived
cross-crate vectors remain integration tests under `tellers-mtproto-testkit/tests`.

## Wire behavior and limits

TL numbers are little-endian. Strings and byte arrays use canonical 1- or 4-byte
length prefixes and zero padding to a 4-byte boundary. Decoding rejects redundant
length forms, invalid padding, trailing input, excessive recursion, aggregate
input, byte lengths, and vector counts. Generated layer types dispatch their own
constructor IDs through codec traits, allowing adapters for multiple pinned
layers.

Transport decoders are incremental: `Incomplete` reports the required buffer
size and `Packet::consumed` preserves a following packet. Full transport checks
sequence and CRC before advancing receive state. Padded-intermediate deliberately
returns payload plus transport padding; only the authenticated encrypted envelope
can identify its message boundary. Obfuscated streams retain AES-CTR state across
partial reads and writes.

Incoming encrypted messages are authenticated before plaintext fields are
returned, then checked for auth-key ID, session ID, message-ID parity/time, body
limits, padding limits, and replay. Gzip expansion is bounded before generated TL
dispatch.

## Integration examples

Encode and decode a bare value:

```rust
use tellers_mtproto_codec::{from_bytes, to_bytes, Limits};

let wire = to_bytes(&42_i64)?;
let value: i64 = from_bytes(&wire, Limits::default())?;
assert_eq!(value, 42);
# Ok::<(), tellers_mtproto_codec::Error>(())
```

Open session state with application-controlled randomness:

```rust
use tellers_mtproto_session::{OsRandom, Snapshot};

let mut state = Snapshot::new(2, &mut OsRandom)?;
state.set_auth_key(vec![7; 256])?;
# Ok::<(), tellers_mtproto_session::Error>(())
```

To send an RPC, implement `tellers_mtproto_engine::Method` for an
application-owned wrapper around the chosen generated request. `encode_request`
and `decode_response` call that layer's codec implementations. Pass the wrapper
to `Engine::invoke`, drain `next_outbound`, add cryptographically random MTProto
padding with `seal_outbound`, then apply the selected transport framing. A
correlated `rpc_result` is delivered through `receive_result` and decoded by
`take_response`; retries keep the typed handle while allocating fresh wire IDs.

A runtime adapter implements only the byte connection boundary:

```rust
use tellers_mtproto_transport::{Connection, Error};

struct MySocket;
impl Connection for MySocket {
    fn send(&mut self, packet: &[u8]) -> Result<(), Error> { /* write_all */ Ok(()) }
    fn receive(&mut self, output: &mut [u8]) -> Result<usize, Error> { /* read */ Ok(0) }
    fn close(&mut self) -> Result<(), Error> { Ok(()) }
}
```

Socket ownership, DNS, TLS, HTTP transfer decoding, timers, cancellation, and
task synchronization belong in separate runtime adapter packages such as
`tellers-mtproto-transport-tokio`.

## Security and state assumptions

Applications must authenticate server RSA keys against a trusted, updateable
key set and apply the crypto crate's DH checks before deriving an authorization
key. `rsa_pad` uses the operating-system CSPRNG; deterministic injection exists
only for reproducible tests. Persisted auth keys and session state should be
encrypted and atomically replaced by the storage implementation. A restored
snapshot is validated before the engine accepts it.

No high-level update, file-transfer, user/chat, storage policy, Secret Chat state
machine, or MTProxy server is implemented here.

## Compatibility and test provenance

Credential-free integration tests reproduce Telegram's published
[authorization-key sample](https://core.telegram.org/mtproto/samples-auth_key),
including plain envelopes, `resPQ`, `pq` factorization, temporary AES, the
encrypted server DH answer, safe-prime/public-value checks, and the final nonce
hash. The transport and service-message behavior follows Telegram's official
[transport](https://core.telegram.org/mtproto/mtproto-transports) and
[service-message](https://core.telegram.org/mtproto/service_messages) documents.

Tests requiring live Telegram credentials are intentionally excluded by default.
Runtime adapters, a trusted-key distribution policy, and live DC interoperability
remain integration responsibilities rather than protocol-core behavior.

## Verification

```sh
just check
just package
# Or reproduce both stages exactly:
just ci
```

The `justfile` exposes the routine commands individually. `cargo xtask ci` owns
the dependency-aware orchestration used by CI, while `cargo xtask package`
verifies dependency-root archives and builds dependent archives in publish order.
Dependent tarballs use `--no-verify` until their new workspace dependencies have
been published; `xtask` supplies local registry patches only while creating those
archives. Release verification then proceeds in dependency order:
codec/crypto/session, transport, engine, and testkit.
